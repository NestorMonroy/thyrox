Revisión 1.3.0: SQLite vuelve a su responsabilidad
--------------------------------------------------

Decidido por el ejecutor el 2026-09-30, con PostgreSQL + pgvector y Redis ya
definidos (ADR-007, ADR-008). SQLite no se elimina: deja de hacer de base de
datos compartida distribuida.

.. code-block:: text

   SQLite                    → persistencia durable local (sesión o instalación)
   PostgreSQL                → persistencia durable compartida y corpus semántico
   Redis                     → coordinación compartida efímera
   RuntimeWorkspace/Snapshot → estado de ejecución y recuperación

**El patrón que desaparece es «SQLite por sesión + Git como sincronización +
merge de filas»** para datos que necesitan una autoridad compartida. Medido en
``thyrox: agent-results/agent_store.sqlite3`` el mismo día: el archivo viaja por
git con ``merge=sqlite-union`` (``.gitattributes:1``) y tiene una tabla
``merge_conflicts`` que sólo existe para ese patrón.

``@thyrox/store`` sigue siendo infraestructura común —conexiones,
migraciones, configuración y transacciones—, con un adaptador SQLite para el
modo local y uno PostgreSQL para el modo compartido; no es una API de dominio.

El archivo no se copia entero a PostgreSQL: se descompone por la naturaleza de
cada dato.

**Dos PostgreSQL por responsabilidad, no por servidor.** La autoridad
compartida de D4-B (dominio de agentes: sesiones, tareas) y el corpus
semántico (documentos, chunks, embeddings, ``analysis_runs``) pueden vivir en
el mismo servidor, con esquemas, puertos y propiedad separados.

**Modo local y modo compartido, sin fallback silencioso.**

.. code-block:: text

   modo local        → SQLite, a propósito
   modo compartido   → PostgreSQL obligatorio
   PostgreSQL caído en modo compartido → error, nunca escribir en SQLite

Escribir en SQLite local cuando la autoridad compartida no responde y
declarar éxito recrearía el split-brain que el merge de filas existe para
reparar. Es la misma regla que la revisión 1.1.0 fija para Redis entre
proxies.
